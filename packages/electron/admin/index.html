    Import / export Entire instance or reviewed content

    Choose an entire stopped instance to keep conversations and sign-ins, or portable content to transfer reviewed files into a fresh agent.

    For a full import, select an empty folder at Welcome and choose “Import an entire instance instead” before installing. To import portable content, create a fresh instance and choose “Import from an fhold export” before completing provider setup; imported task definitions remain inactive until reviewed.

    For automatic same-instance continuity after storage is lost, use Ephemeral container support below. These two options use different formats and are not interchangeable.

    What is included?

    Entire instance includes system, config, knowledge, workspace, state and data: native conversations, sign-ins, credentials, permissions, plugins and active task settings. Only process coordination is omitted. Portable content includes reviewed knowledge, workspace, allowlisted settings and inactive task definitions. No native conversations or remote sign-ins in portable content. Neither option captures external drives, named volumes, external symlink targets or container images.

    Stop the instance in Overview first. All containers and other writers must stay stopped until export finishes. The unencrypted export includes private sign-ins and access keys. Import it into an empty folder, and never run both copies together. Export does not automatically stop or restart containers.

    Advanced checkpoint settings

    These bound recovery work, not a zero-loss guarantee. fhold sets the container’s termination grace to allow writer shutdown and a final checkpoint. Recovery is independent of scheduled tasks.

    One absolute container path per line; no glob or home expansion. Existing native databases are already included. SQLite is snapshotted consistently, including committed WAL changes; it is never a live file copy. Paths must already be accessible in the container—this does not mount drives.

    Ordinary local volumes remain covered. Missing required mounts stop recovery. Native or registered SQLite files and their WAL/SHM cannot be excluded or placed on recognized network filesystems.

    Changing established mount ownership requires a stopped-writer transition to a new recovery namespace, not editing old receipts. Additional paths/databases may be added, but removing captured coverage is refused by the native engine.

    Editable policy file: config/recovery/include.json

    Initialize or restore while stopped

    Save the settings, stop this instance, then initialize a genuinely new destination once. Start it to publish its first checkpoint. For an existing namespace, do not initialize again: startup restores automatically before writers run. Offline validation/restoration leaves containers stopped and never overwrites surviving local data.

    A stale owner needs separate, explicit stopped-writer verification; Admin never takes over a lock automatically. Retain the original disk/checkpoints until cold recovery is verified.
